# 1.1 tickets: several activities per topic, and plain practice

The spec is core `docs/DESIGN.md` §2 "1.1 scope" (B1 to B5), §7 and §8, and `docs/desktop/DESIGN.md` §3.2, §4.3, §4.5, §4.14, §4.15 and §9 (B6 to B11). One ticket is one PR into `staging`, titled as a conventional commit.

Every ticket works test-first: write the failing tests named here, make them pass simply, then refactor while green. Run only the affected tests locally (`npm run test:unit -- <files>` for core, the touched desktop test files for the desktop) and let CI run the rest. Keep every `AGENTS.md` invariant. No co-author lines, and no mention of CodeChum.

## t1. Learner rules for 1.1

- **Criteria:** B1, and the pure rules behind B2 (`more`), B3 (`unlock`) and B4 (status).
- **Specialist:** core engineer. **Depends on:** the spec.
- **Files:** `src/learner.ts`, `src/schemas.ts`, `test/learner.test.ts`, `test/schemas.test.ts`.
- **Build:** add the `unlock` event to `LearnerEventSchema`; `replay` skips it, and `nextStep` gives no `lesson` field for a concept that has one. Add `ahead: { difficulty }` to `practice` steps by computing `nextStep` again on the log plus a perfect check of the step's exercise at the same `now` (DESIGN §7 "Ahead"). Add a pure `moreStep(roadmap, exercises, log, lessons, concept)` that returns the `practice` or `author` step for a reached concept (the earliest never-checked exercise at its current difficulty, or else `author` at that difficulty, each with the concept's `lesson` field) and says when the concept isn't reached, and a pure `exerciseStatus(log)` that gives each exercise's `checked` and `passed`.
- **Failing tests first:** every case in B1 (first activity at difficulty 1 gives 2; after a failed check, 1; at difficulty 3, 3; assisted gives the current difficulty; none when another exercise at that difficulty has no perfect check, when the pass would master the concept, or while a lesson is unread); `unlock` removes the `lesson` field, also for a lesson saved after it, and replay is identical with and without it; `moreStep` on a mastered concept, on a candidate, with a never-checked exercise at the difficulty, with only checked ones, and on an unreached concept; `exerciseStatus` for no check, a failed check and a perfect one; the schema accepts `unlock` at `format_version` 1.

## t3. Core: next_step requests, unlock, exercise status and the author brief

- **Criteria:** B2, B3, B4, B5.
- **Specialist:** core engineer. **Depends on:** t1.
- **Files:** `src/app/exercises.ts`, `src/app/lessons.ts`, `src/app.ts`, `src/mcp.ts`, `src/templates.ts`, `test/app.test.ts`, `test/mcp.test.ts`, `test/package.test.ts`, `test/templates.test.ts`.
- **Build:** `app.nextStep(ws, bound?, request?)` with `{ ahead: true }` or `{ more: concept }`: `ahead` turns a `practice` step with `ahead` into the full `author` step (title, style, track, contract, earlier, lesson; one helper builds the author fields for both paths), and `more` validates the concept against the roadmap and calls `moreStep`, failing with a plain message for an unknown or unreached concept. Both give `setup` while the track isn't installed. `next_step`'s input schema takes `ahead` or `more`, never both. `app.unlockActivity(ws, concept, bound?)` appends `unlock` once under the course lock. `app.listExercises` adds `checked` and `passed`. `JOB_BRIEFS.author` and the terminal author file say to call `next_step` with the brief's request, if any, and to end without saving unless the step is `author`.
- **Failing tests first:** `next_step` with `ahead` returns an author step with the track's contract, and returns other steps unchanged; with `more` on a mastered concept, on an unreached one (error), on an unknown one (error), and with both inputs (error); a canary exercise's hidden strings never appear in either result; `unlockActivity` records once, refuses an unknown concept and opens the gate; `listExercises` reports `checked` and `passed`; the packed stdio server answers `next_step` with each request; the brief text.

## t4. Desktop main: follow ahead, More practice, I know this, the series

- **Criteria:** B6 (all targets), B7, B8 (data), B9 and B10 (main), B11 (mock).
- **Specialist:** desktop engineer. **Depends on:** t2, t3.
- **Files:** `desktop/src/main/live.ts`, `courseView.ts`, `views.ts`, `ipc.ts`, `agent/briefs.ts`, `core/types.ts`, `mock.ts`, `testing/contract.ts`, `desktop/src/shared/api.ts`, and their tests.
- **Contract** (`shared/api.ts`, for t5 too): `activity(concept, id?)` opens the topic's activity on offer, or the activity `id` of that topic; `morePractice(concept): Promise<string | null>` gives the activity id to open, or null while one is being written; `unlockActivity(concept): Promise<void>`. `TopicView.activities: { id, number, passed, current? }[]` and `Activity.number?` (absent for a review). Ids stay opaque and are never shown.
- **Build:** `work()` queues the ahead author job (`briefs.author({ ahead: true })`, keyed by concept and the ahead difficulty, done by any new exercise for the concept); `morePractice` asks core for `more` and starts a More practice job for an `author` answer; t2's "still wanted" check covers both; `unlockActivity` calls core and schedules; `courseView` builds `activities` from `listExercises` (numbers, `checked`, `passed`, the one on offer) and `exerciseFor` opens the activity checked last for a stuck topic. The mock implements all of it, with states for each new screen.
- **Failing tests first** (fake core, fake agents, and the shared contract on both mock and live): B7's two cases; a pass while an ahead job runs starts no second job; `morePractice` on a mastered topic writes one activity and then returns it, returns an untried one without a job, and is refused on a later topic; `unlockActivity` opens a lesson-locked activity; `activities` lists checked ones and the one on offer, not one written ahead, with numbers in save order; `activity(concept, id)` refuses another topic's id; a stuck topic opens the activity checked last; the IPC validates the new arguments.
