# 2026-10-24

## Agents and Docker found wherever their installers put them

**What changed**: on Windows 11 (beta.4), an agent installed while Codemm was open stayed "Not installed" until a restart. Codemm read `PATH` only at launch, and its lookup missed several official install folders. This is the first of several PRs for zero setup friction on macOS and Windows.
- **Windows live PATH** (`desktop/src/main/agent/livePath.ts`). Before Connect's list, Connect, Check this computer and each job's start (`live.ts`), Codemm reads the machine's and the user's `Path` with `C:\Windows\System32\reg.exe` as argument arrays. It expands REG_EXPAND_SZ `%NAME%` as Windows builds a new process's environment (Codemm's own variables, then the machine's and the user's from the same keys, so nvm-windows' `%NVM_HOME%` or pnpm's `%PNPM_HOME%` defined mid-session expand too), and appends the missing folders to `process.env.PATH`, so jobs and core's docker calls inherit them. What PATH had is never removed or reordered. Calls at the same time share one read, and a read under 2 seconds old is reused. A read that fails or takes over 2 seconds keeps the PATH, and after one that hung or threw the next waits 30 seconds. The clock is monotonic. Off Windows, or with `CODEMM_TEST_FIXED_PATH` (set by the packaged and install tests, which stage a PATH), it does nothing. `find` stays synchronous.
- **More folders** (`find.ts`): WinGet's command links (`%LOCALAPPDATA%\Microsoft\WinGet\Links`, `%ProgramFiles%\WinGet\Links`), Cursor's `%LOCALAPPDATA%\cursor-agent` (its `.cmd` is still passed over until the Cursor-launcher PR), Docker Desktop's per-user CLI folder on Windows (`%LOCALAPPDATA%\Programs\DockerDesktop\resources\bin`), and `~/Applications/Docker.app/Contents/Resources/bin` on macOS. `dockerDesktops(where)` is the one list of Docker Desktop's installs (app and CLI folder, all users and per user); `find.ts`'s folders and `dockerDesktop.ts`'s apps both derive from it. `find()` keeps splitting PATH on this computer's separator, like `here()` and `withDockerFolders`.
- **npm shims for a native binary**: `shimTarget` takes the quoted path just before `%*`. A `.exe` target runs directly if it starts with `MZ`, which finds Claude Code installed with npm (its `bin` is `bin/claude.exe`, a text placeholder until its postinstall runs). The JS shim's `IF EXIST "%dp0%\node.exe"` line is no longer a candidate.
- **macOS `~/Applications/Docker.app`** (`dockerDesktop.ts`): counts as installed, Open Docker Desktop opens it, and Install Docker opens an existing Docker.app from either Applications folder instead of downloading.
- DESIGN (desktop) §3.1 and §6.1 say so.

A second review (the parent session's) added: expanding registry-defined variables, one list of Docker's installs, one name (`livePath`), literal paths in the Docker test, and consistent PATH separators. It also asked that no literal `%NAME%` reach PATH, and for the dead `%~dp0` alternative to go. All are done; the PowerShell fallback is deferred.

**Verified**: tests written first and seen failing. Desktop typecheck passes, and so do the affected tests on macOS (livePath, find, dockerDesktop, the new `live.path` tests, every `live.*` file, connect, computer, agent, agentInstall, server and mock). New tests:

## Cursor's CLI on Windows

**What changed**: on Windows, Cursor was never found, even after a relaunch. Its `cursor-agent.cmd` is a PowerShell 5.1 launcher, not an npm shim, and Codemm can't run a `.cmd` without a shell. `agent/cursorWindows.ts` now resolves Cursor's install root to `versions\<v>\node.exe` and `versions\<v>\index.js`. `Executable` takes optional leading `args` and `env`, and `bridge.command` builds every launch from them, for jobs, status checks and Sign in. Cursor runs as `node.exe index.js …` with `CURSOR_INVOKED_AS=cursor-agent.cmd` and, unless one is set, `NODE_COMPILE_CACHE`, as its own `cursor-agent.ps1` runs it (a `node.exe` beside the launcher included). The version choice follows that launcher too. Its text (2026.10.22-27dcf5f) came from the CI install matrix's Windows runner (PR #226): the newest version folder by date, with no `--use-system-ca`, unlike the macOS launcher. On Windows, `find.ts` sends a `cursor-agent.cmd` that isn't an npm shim to the resolver. #228 put `%LOCALAPPDATA%\cursor-agent` among the searched folders. `killTree` runs `taskkill` by its full path. DESIGN (desktop) §3.1 says so.

**Verified**: tests written first: resolver fixture trees (one version, several, timestamped, `.new`/`.previous`/temporary, a missing `node.exe`, `node.exe` beside the launcher, none), the launcher's environment, `spawnable` and `command` with the prefix, `find` for Cursor's real `.cmd` (not found with no version, found once there is one, and a `node.exe` beside the launcher), Sign in for Cursor on win32, taskkill's full path, and a real child that gets a brief with newlines, quotes, `!`, `%PATH%` and backticks byte for byte (CI runs it on Windows too). Desktop typecheck and the affected test files pass on macOS.

**Not verified**: a real Windows PC. Still to confirm there: the version choice, and a full Cursor job and sign-in. A staged self-update waits until Cursor runs from a terminal, because Codemm skips the launcher's `promote-staged.cmd`.

**Next**: confirm on a Windows PC or the CI install matrix. Codemm installing Cursor is a separate PR.
