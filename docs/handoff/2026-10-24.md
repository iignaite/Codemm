# 2026-10-24

## Cursor's CLI on Windows

**What changed**: on Windows, Cursor was never found, even after a relaunch. Its `cursor-agent.cmd` is a PowerShell 5.1 launcher, not an npm shim, and Codemm can't run a `.cmd` without a shell. `agent/cursorWindows.ts` now resolves Cursor's install root to `versions\<v>\node.exe` and `versions\<v>\index.js`. `Executable` takes optional leading `args` and `env`, and `bridge.command` builds every launch from them, for jobs, status checks and Sign in. Cursor runs as `node.exe index.js …` with `CURSOR_INVOKED_AS=cursor-agent.cmd`, as its own `cursor-agent.ps1` runs it. The version choice follows that launcher too. Its text (2026.10.22-27dcf5f) came from the CI install matrix's Windows runner (PR #226): the newest version folder by date, with no `--use-system-ca`, unlike the macOS launcher. `find.ts` sends a `cursor-agent.cmd` beside a `versions` folder to the resolver. DESIGN (desktop) §3.1 says so.

**Verified**: tests written first: resolver fixture trees (one version, several, timestamped, `.new`/`.previous`/temporary, a missing `node.exe`, none), `spawnable` and `command` with the prefix, Sign in for Cursor on win32, and a real child that gets a brief with newlines, quotes, `!`, `%PATH%` and backticks byte for byte (CI runs it on Windows too). Desktop typecheck and the affected test files pass on macOS.

**Not verified**: a real Windows PC. Still to confirm there: the version choice, and a full Cursor job and sign-in. A staged self-update waits until Cursor runs from a terminal, because Codemm skips the launcher's `promote-staged.cmd`.

**Next**: confirm on a Windows PC or the CI install matrix. Codemm installing Cursor is a separate PR.
