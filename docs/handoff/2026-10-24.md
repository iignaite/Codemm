# 2026-10-24

## Agents and Docker found wherever their installers put them

**What changed**: on Windows 11 (beta.4), an agent installed while Codemm was open stayed "Not installed" until a restart. Codemm read `PATH` only at launch, and its lookup missed several official install folders. This is the first of several PRs for zero setup friction on macOS and Windows.
- **Windows live PATH** (`desktop/src/main/agent/livePath.ts`). Before Connect's list, Connect, Check this computer and each job's start (`live.ts`), Codemm reads the machine's and the user's `Path` with `C:\Windows\System32\reg.exe` as argument arrays. It expands REG_EXPAND_SZ `%NAME%` as Windows builds a new process's environment (Codemm's own variables, then the machine's and the user's from the same keys, so nvm-windows' `%NVM_HOME%` or pnpm's `%PNPM_HOME%` defined mid-session expand too), and appends the missing folders to `process.env.PATH`, so jobs and core's docker calls inherit them. What PATH had is never removed or reordered. Calls at the same time share one read, and a read under 2 seconds old is reused. A read that fails or takes over 2 seconds keeps the PATH, and after one that hung or threw the next waits 30 seconds. The clock is monotonic. Off Windows, or with `CODEMM_TEST_FIXED_PATH` (set by the packaged and install tests, which stage a PATH), it does nothing. `find` stays synchronous.
- **More folders** (`find.ts`): WinGet's command links (`%LOCALAPPDATA%\Microsoft\WinGet\Links`, `%ProgramFiles%\WinGet\Links`), Cursor's `%LOCALAPPDATA%\cursor-agent` (its `.cmd` is still passed over until the Cursor-launcher PR), Docker Desktop's per-user CLI folder on Windows (`%LOCALAPPDATA%\Programs\DockerDesktop\resources\bin`), and `~/Applications/Docker.app/Contents/Resources/bin` on macOS. `dockerDesktops(where)` is the one list of Docker Desktop's installs (app and CLI folder, all users and per user); `find.ts`'s folders and `dockerDesktop.ts`'s apps both derive from it. `find()` keeps splitting PATH on this computer's separator, like `here()` and `withDockerFolders`.
- **npm shims for a native binary**: `shimTarget` takes the quoted path just before `%*`. A `.exe` target runs directly if it starts with `MZ`, which finds Claude Code installed with npm (its `bin` is `bin/claude.exe`, a text placeholder until its postinstall runs). The JS shim's `IF EXIST "%dp0%\node.exe"` line is no longer a candidate.
- **macOS `~/Applications/Docker.app`** (`dockerDesktop.ts`): counts as installed, Open Docker Desktop opens it, and Install Docker opens an existing Docker.app from either Applications folder instead of downloading.
- DESIGN (desktop) §3.1 and §6.1 say so.

**Review**: one independent Opus review. These findings were verified and fixed: e2e staging lost to the refresh (test switch), npm's placeholder `claude.exe`, the wall clock, a non-hermetic Docker test, two tests that passed without the fix, and no back-off after a hung reg.exe. A second review (the parent session's) added: expanding registry-defined variables, one list of Docker's installs, one name (`livePath`), literal paths in the Docker test, and consistent PATH separators. It also asked that no literal `%NAME%` reach PATH, and for the dead `%~dp0` alternative to go. All are done; the PowerShell fallback is deferred.

**Verified**: tests written first and seen failing. Desktop typecheck passes, and so do the affected tests on macOS (livePath, find, dockerDesktop, the new `live.path` tests, every `live.*` file, connect, computer, agent, agentInstall, server and mock). New tests:
- reg output parsing, expansion, merge and dedupe;
- one shared read, a young result reused, the PATH kept when reg fails or hangs past 2 seconds, and a merge that never shrinks or reorders PATH;
- fixture trees for WinGet, Cursor's folder, the npm `.exe` shim (cmd-shim's real no-shebang template), Docker per-user and `~/Applications`;
- through the live API: an agent and a docker that appear only in the registry PATH after start show on the next `agents()` and `computer()`, and a job refreshes before it starts.

**Not verified**: nothing has run on a Windows PC yet. The Windows unit tests run only in CI.

**Next**:

GitHub's Windows runner already confirmed Docker's per-user CLI folder (`%LOCALAPPDATA%\Programs\DockerDesktop\resources\bin\docker.exe`, added to the user PATH) and WinGet's `Links\claude.exe` and `codex.exe` symlinks (ci-install-findings, PR #226).
- **PowerShell fallback** (deferred, DESIGN §12): when a policy blocks reg.exe, the PATH stays as launched. The fixed folders still find every vendor's install.
- **Older shims**: old npm, pnpm and yarn shims write `"%~dp0\..."`, which `shimTarget` doesn't read (its dead `%~dp0` alternative is removed). `bridge.ts`'s `taskkill` by bare name went to the Cursor-launcher session.
- **Non-ASCII folder names**: reg.exe writes in the console's code page, so a folder whose name has non-ASCII letters can be misread, and one it can't spell is left out. The fixed folders don't depend on it.

## Docker Desktop and WSL on Windows without the installer's prompts (branch `fix/windows-docker-wsl`)

What changed:
- Docker's Windows install is now Docker's own per-user install, unelevated: `install --user --quiet --backend=wsl-2`. No permission prompt, no installer window, no install-type page. No `--accept-license`: Docker's Accept stays in Docker Desktop's first window (DESIGN §6.1, item 5). An existing Docker Desktop, for all users or this one, is never installed over. Exit 1603 and every other non-restart code is "failed".
- New `desktop/src/main/wsl.ts`: reads firmware virtualization, the hypervisor and the Virtual Machine Platform feature (PowerShell CIM, once per run, 15 s), a pending restart (RebootPending), WSL's presence (`%ProgramFiles%\WSL\wsl.exe`) and version (`wsl.exe --version`, `WSL_UTF8=1`), and runs WSL's own setup (`--install --no-distribution` or `--update`) as administrator. The .NET `runas` script, `REG` and the restart moved to `windows.ts`.
- Install Docker on Windows runs WSL's setup first when it's needed (one prompt), then Docker's install, then asks for a restart instead of opening Docker. Check this computer's running row names the real cause (WSL missing, WSL old, virtualization off, restart pending) instead of "Docker is starting" or Open Docker Desktop, with Set up WSL, Update WSL or Restart now. `restartWindows` is a new IPC call: `shutdown.exe /r /t 0`, on the learner's click only.
- Not done, on purpose: reopening Codemm after the restart (HKCU RunOnce) is an owner decision, listed in DESIGN §12. `Setup.tsx` is unchanged (another session owns it), so Setup's Docker card shows the restart line without a Restart now button for now.

How it was verified:
- Test-first unit tests: `wsl.test.ts` (parsing UTF-8, UTF-16 and localized output, each state, the elevated arguments, nothing elevated when nothing is needed), `dockerDesktop.test.ts` (argument array, no runas, exit codes, WSL first, no reinstall), `computer.test.ts` (each WSL cause replaces starting), renderer `computer.test.tsx` and `setup.test.tsx` (each state's screen; nothing restarts without a click).
- CI's Windows runner runs `wsl.test.ts`'s real-command test: WSL reads ready there (WSL 3.0.3, the Virtual Machine Platform on, a hypervisor).
- Two throwaway CI probes (notes in the session group's `docker-wsl-probe.md`): Docker's installer with Codemm's exact arguments, no `--accept-license`, exits 0 in 46 s and puts `docker.exe` and `Docker Desktop.exe` per user; its manifest is `asInvoker`, so a standard user gets no error 740. That's why there's no elevated fallback. The install matrix now checks the manifest and the app on every run.
- Two Opus reviews (this session's and the coordinator's), each finding verified and fixed or answered in the PR.
- Not confirmed on a real PC: the exit code of `wsl --install --no-distribution` on a PC without WSL, `Win32_OptionalFeature` read by a standard user (unread, Codemm falls back to the hypervisor flag), RebootPending after WSL's setup, and Windows 10 22H2's own wsl.exe with `--no-distribution`.

What's next:

- Once the Setup screen's owner merges: a Restart now button in Setup's Docker card, and the WSL step there instead of Open Docker Desktop.
