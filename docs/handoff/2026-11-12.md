# 2026-11-12

## The roadmap shows before its review ends

**Why**: the app's own log (the owner's Mac, beta.10, Claude Opus) showed that a new learner waited for research (157 s) and then the roadmap review (112 s) before seeing anything: 4.5 minutes of a first run of about 5. Setup and the first activity already run in the background while the first lesson is written (desktop DESIGN §3.2), so the review was the largest wait the learner could not use.

**What changed** (desktop DESIGN §3.2 and §4.9):

- Research is done once its sources save, and the roadmap opens at once. The review then runs in the foreground lane while the learner reads the roadmap.
- The learner's first edit, change request or Approve stops the review and waits until its agent is gone, then saves (`saveConcepts` in `live.ts`). The learner's roadmap always wins. A review whose agent survives its cancel refuses the edit with the usual "Codemm couldn't stop your agent. Quit Codemm to stop it." (§3.1).
- The review starts before research reports done, so an edit always finds it to stop.
- The editor says "Codemm is double-checking this path. You can edit or approve it now." while the review runs. If the review ends before any edit, the editor reads the draft again, so the review's corrections show.
- The sidebar opens a running review in the roadmap editor, not on the research screen, where a finished research would start again. The research screen shows research progress only.
- The mock plays the review beside the roadmap and stops it on an edit or Approve, as live does.

**Verified**: desktop `npm run typecheck`, and the full desktop Vitest suite passed twice (1109 passed, 11 skipped). Each new test failed first: the review running beside a shown roadmap, an edit, change request or Approve stopping it (with a review save that lands during the stop), the refused edit when the review can't be stopped, the editor's note and reload, an edit kept when the review ends later, and the sidebar opening the editor. Two older tests now wait for the review, which ends after research reports done. One unrelated renderer test (`lessons.test.tsx`, io example in the terminal pane) failed once under full-suite load and passed 5 times on its own.

**Live check** (the unpackaged app built from this branch, real agents, on macOS with Docker running; a temp `CODEMM_HOME`, workspace and Electron profile, API-key variables removed, the learner's real data checked unchanged). Goal "Python functions", known "variables and print", then Approve as soon as the roadmap showed:

| Agent (model) | Roadmap shown after | Review note shown | Approve to next screen | Review job | Review processes after Approve | Saved roadmap |
|---|---|---|---|---|---|---|
| Claude Code (sonnet) | 48.5 s (research 47.4 s) | yes | 1.5 s | cancelled after 2.0 s | none | the 17 topics shown |
| Codex (gpt-6-luna) | 87.7 s (research 86.3 s) | yes | 0.5 s | cancelled after 1.2 s | none | the 20 topics shown |

No process from either run was left afterwards.

**Fixed after review (#279's follow-up)**: a review's save makes its course active, so researching a new course now stops the last draft's review first. A review no longer starts once the learner has edited or approved the draft, and after a review's agent survives its cancel, every later edit and Approve of that roadmap is refused until quit, not only the first.

**Not verified**: the e2e and packaged suites, a review stopped in the middle of a save (both live stops came within 2 s of its start), a review that ends on its own with the editor showing its corrections (covered by unit tests only), Cursor, and Windows.

**Next**: time a fresh first run on macOS and Windows and compare with the numbers above.

## A reason to come back: practice time and the next review

**Why**: the app's update checks fell from about 74 a day in the friends' beta (late October) to under 2 a day after 31 Oct. Learners didn't come back. Reviews come due 1, 3, 7, 21 and 60 days after mastery, but nothing outside the app reminded anyone, and the review card and streaks were cut from 1.0 (desktop DESIGN §12).

**What changed** (desktop DESIGN §3.2 and the new §4.15):

- **Practice time.** The course map's side column has a "Practice time" card: a time (default 19:00) and "Every day" or "Weekdays". Save to calendar asks where to save, with the system's save dialog, and writes `Codemm practice.ics`: one repeating 30-minute event, "Practice with Codemm", at that local time, with a reminder. Its description names the course and says a due review comes first, then the next topic. Codemm keeps no copy and opens nothing. Cancelling saves nothing.
- The file is built in `main/calendar.ts` (RFC 5545: CRLF, TEXT escaping, folding at 75 octets without splitting a character, floating local time, today if the time is still ahead, otherwise tomorrow).
- IPC `savePracticeTime({ time, repeat })` validates `HH:MM` and the two choices; the renderer never names a path. `wire.ts` shows the save dialog.
- **Review line.** A passing Check that leaves the topic with a scheduled review says when under "You mastered …": "Review tomorrow." or "Review in N days.", from core's `reviewDue`, with the same day count the course map uses (`reviewDays` in `courseView.ts`).
- A file of review dates was not built: core knows only each topic's next review, so it would be out of date after the first one. §4.15 says so.

**Verified**: desktop `npm run typecheck`, and the full desktop Vitest suite (1115 passed, 11 skipped). Each new test failed first: the calendar file (start today or tomorrow, a month end, weekdays, escaping and folding with multibyte characters), the IPC check, the main-process save and cancel, the review days in a check, the results line, and the card. The built app on the mock showed the card on the course map and its saved message.

**Fixed after review**: a weekdays series now starts on the next weekday, not a weekend. The chosen time is written as chosen, so a time in an hour a clock change skips isn't moved. A lone carriage return and other control characters can't reach the file. Each course keeps one event series (a stable UID and a growing SEQUENCE). The renamed course name is used, and a file that can't be written says so in words instead of the general error screen.

**Not verified**: the real save dialog and an import into a calendar app (Calendar, Outlook, Google Calendar). The mock saves no file.

**Next**: import a saved file into Calendar on macOS and Outlook on Windows. Then the "Today" card (reviews due, days practised this week) from the marketing report's R4.
