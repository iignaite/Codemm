# 2026-10-20

## Friends' feedback on 1.0.0-beta.3

Five issues from friends who tried the beta, one PR each, from `e68a78f5`. Every PR was reviewed by a separate read-only Opus agent, and its findings were fixed in the same PR.

**What changed**

- **Continue after a pass did nothing about half the time** (#212). A pass that doesn't master a topic yet leads Continue to the same topic's next activity, the practice route already on screen. `App.tsx` keyed the activity screen by its topic, so it never remounted and the passed result stayed. The screen now opens fresh on every visit, and a sidebar item that leads to the screen on show does nothing, so Practice on Practice keeps results, a running program and unsaved code. The mock's `passes` option acts out a pass that doesn't master.
- **Windows 11 22H2** (#213). The step says why and offers **Open Windows Update** (`C:\Windows\explorer.exe ms-settings:windowsupdate`, an argument array). Windows Server is its own problem with no such step. No older Docker Desktop is offered: Docker supports it only on Windows versions still in Microsoft's servicing, and an old release misses its security fixes.
- **Docker's memory** (#214). One README "Good to know" bullet: where a Mac lowers it, that WSL sets it on Windows, and that too low a limit can make setups and checks fail. No floor and no promises.
- **"Does Practice send me to learning?"** (#215). The sidebar's Practice opened the topic page (lessons) whenever the activity wasn't open, and Learn lit up. Practice now always opens the Practice screen for the topic Codemm offers now (`offeredTopic`, shared with the course map). Until the activity opens, the screen says why (lessons first, setup, or being written with its progress), offers Go to the lessons, and opens the activity by itself with focus. The slim sidebar's icons have tooltips.
- **Colored code in the editor** (this PR). highlight.js's common build (BSD-3-Clause), lazy-loaded with the first editor, colors a file by its extension through highlight.js's own alias table, so Codemm names no language. The copy lies under the textarea, which stays the editor.

**Verified**: desktop typecheck and the affected renderer and main tests on macOS (the whole renderer suite on the highlighting branch); a renderer build shows highlight.js only in its own chunk (165 KB, 55 KB gzipped) and in `licenses.md`. Coloring a 64 KB file took about 28 ms per keystroke, so the cap is 32 KB. Before and after shots came from the mock in a scratch Vite page.

**Not verified**: a real Windows 11 22H2 PC (Open Windows Update is tested against a fake `launch`); the real core's mastery path behind Continue (the mock stands in); typing with an input method (Japanese, Chinese) in the colored editor, whose composition underline may take the textarea's transparent color.

**Next**

- Once #215 is in, Continue could open Practice's waiting screen instead of the topic page while the topic's next activity is written.
- Lesson code blocks could use the same highlighter, with the fence's info string as the data.

## Lesson code colors

**What changed**: lesson code blocks use the editor's highlighter (the last Next item above). The loader moved to `renderer/ui/colors.ts`, and `colorize` now takes the name highlight.js is asked about: the editor passes a file's extension, a lesson the first word of a fence's info string. `useLessonParts` loads highlight.js only for a lesson with a fence that has an info string, and a lesson or editor opened after it loaded is colored on its first paint; the token colors in `app.css` cover `.md pre` too, each AA on its `--soft` background. DESIGN §2.1, §4.3 and §4.10 say so.

**Verified**: desktop typecheck and the ui, lessons, practice and styles tests on macOS, a before and after shot from the mock in a scratch Vite page, and a read-only Opus review (its three small findings are fixed, including `desktop/HANDOFF.md`'s stale line on highlighting). A test checks that a lesson with only a plain fence and indented code loads no highlighter, and fails when that fence gets an info string.

**Not verified**: the colors in the running app (no build here: low disk). Activity statements and the tutor's replies still show code plain.

## Statement and reply code colors

**What changed**: activity statements and the tutor's replies color their code as lessons do (the last Not verified item above). `Markdown` renders with the same `highlight` option and loads highlight.js only for text with a fence that has an info string; it shares the options, the `code` check and the loading effect with `useLessonParts`. It memoizes its render, so the practice screen's keystrokes and the rail's composer and progress no longer re-parse the statement or each reply. DESIGN §2.1, §4.3 and §4.10 say so.

**Verified**: desktop typecheck and the ui, practice, lessons, course and styles tests on macOS. A rail test checks that replies without a fence that names its code load no highlighter, and fails when the load is forced; parser-spy tests check that typing re-parses nothing. Before and after shots from the mock in a scratch Vite page: the statement's and the reply's fences are plain on #218 and colored here, on `--soft` (the lowest token color is 4.78:1). A read-only Opus review found no code problems; its order-dependent test and doc wording are fixed.

**Not verified**: the colors in the built app (no build here: low disk).
